# Supplier Quality Risk Agent

An agent that answers questions about supplier defect data by deciding, per
question, whether the answer lives in a database, in corrective action
reports, in both, or in neither — and shows its reasoning.

**Live:** [supplier-quality-agent.vercel.app](https://supplier-quality-agent.vercel.app)
The first request may take up to a minute; the backend sleeps on a free tier
and the routing call is a real API call.

---

## The problem it exists for

Two suppliers in the dataset show a defect-rate increase in mid-2026. In SQL
they look the same — a monthly PPM figure climbing over several months.

The correct response is opposite.

**SUP-003** is a real degradation. Welding electrode tips are wearing past
their dressing interval, the same failure that was fixed in early 2025 and
has recurred since a controller was replaced. It needs a supplier corrective
action request.

**SUP-001** is not a supplier problem at all. The incoming inspection fixture
had drifted out of calibration. The supplier's own CMM data showed every part
conforming, and a gauge R&R confirmed the measurement system was at fault.
The recorded PPM for those months overstates the real defect rate.

No query distinguishes them, because the defect table looks identical in both
cases. Only an 8D report says which is which. An agent that answers from SQL
alone will confidently send someone to chase a supplier who did nothing
wrong.

That is what this project is about: **a number and a document can disagree
about what is true, and a system that cannot tell the difference will mislead
you fluently.**

Try it: ask *"SUP-001's PPM rose in mid-2026. Should we raise a corrective
action request?"*

## How it works
question
│
▼
router ──── SQL ─────► query catalogue (8 fixed parameterised queries)
│ typed parameters, existence checks, 4 failure kinds
├──── DOCS ────────► pgvector over 13 8D reports, 104 chunks
│ open and closed grouped separately
├──── BOTH ────────► both, when neither alone is a complete answer
└──── NEITHER ─────► declines, and says what is missing

Every response carries its provenance: which route was chosen and why, the
SQL statement that ran, the passages retrieved with their distances, and the
latency of each step.

**Stack:** FastAPI, Postgres 18 with pgvector (Neon), Gemini for routing and
embeddings, one static HTML page. Deployed on Render and Vercel.

## What is worth looking at

**The router is measured, not asserted.** 21–22 of 24 on a labelled question
set, across five runs — reported as a range because three questions flip
between runs and a single run's number would be noise.
[`eval/routing-set.json`](eval/routing-set.json)

**The eval set was frozen before the router existed.** The ground-truth rule
was committed first, then the questions, then the router. The git history
shows that order, which is the only thing that makes the number mean
anything. [`docs/routing-rule.md`](docs/routing-rule.md)

**Two labels were wrong and are corrected in the open**, with the reasoning
and the date recorded next to them. The test applied each time: does the
correction improve the system, or only the number?

**The agent declines.** Ask about on-time delivery and it consults nothing,
because no source holds it. Ask about a supplier that does not exist and it
says so rather than returning zero rows that read as "no defects".

**Chroma was replaced with pgvector after measurement.** A clean install of
the deploy requirements came to 476 MB against a 512 MB limit, almost all of
it unused transitive dependencies. Moving vectors into Postgres brought it to
107 MB. The migration was verified by re-running the retrieval tests: cosine
distances matched to four decimal places.

The full reasoning for every decision, including the ones that were rejected,
is in [`docs/design-decisions.md`](docs/design-decisions.md).

## The data

Entirely synthetic and generated by
[`backend/db/generate_data.py`](backend/db/generate_data.py) — 10 suppliers,
50 parts, 24 months of production volume, 4,725 defect events and 13 8D
reports, seeded and reproducible.

It models general body-in-white quality practice: PPM as the defect rate, the
8D format for corrective actions, defect severity, incoming inspection. No
proprietary data of any kind is used or represented.

Five patterns are planted deliberately so questions have a known correct
answer — a trend, a spike, a concentration, a measurement artefact, and a set
of low-volume parts that make "which parts had no defects" answerable. Every
figure quoted in the docs is measured from the generated data rather than
intended.

## Running it

```bash
cd backend
pip install -r requirements-dev.txt
cp .env.example .env          # add a Neon URL and a Gemini key

python db/apply_schema.py
python db/generate_data.py
python tools/index_documents.py

uvicorn api:app --reload --port 8000
```

Then serve the frontend:

```bash
cd frontend && python -m http.server 3000
```

To score the router against the eval set:

```bash
python backend/agent/score_routing.py
```
